## Upgrade and rollback

This is a future deployment runbook, not a command to promote now.

1. Verify the completed requalification in #233 and operator authorization.
   Record the exact signed release tag, source commit and built image ID.
   Builds use the existing Portainer Git stack; no GHCR image is implied.
2. Record the target instance, existing image, private configuration and
   all persistent mounts. Staging and production must have distinct
   credentials, calendars, inboxes, databases and volumes.
3. Stop only the selected instance. Back up its complete database/inbox/media
   state and configuration privately; preserve UID 10001 access. Verify
   SQLite integrity, foreign keys and the file hash manifest.
   The [staging preparation guide](phase-9-staging-preparation.md) supplies
   a stopped /data backup example; adapt it to actual reviewed mounts.
4. Freeze the existing stack to the approved immutable release reference.
   Preserve its persistent volume, Graph target and existing source jobs.
   Startup applies migrations 013 and 014; do not recreate the database.
5. Enable the optional manual runtime and install profiles using the
   [workflow](manual-import-workflow.md). Match the target instance identity
   and explicitly review any stage-authority changes.
6. Prepare production-specific manifests and approvals from the reviewed
   source records. Never copy staging SQLite, inbox markers, approvals or
   Outlook mappings into production. Run a fresh target preview, approve
   that exact fingerprint and verify APPLIED plus Outlook convergence.
7. Verify healthy startup, schema 014, expected existing mappings, import
   receipts, reminder fields and an unchanged cycle. Keep private evidence.

If upgrade acceptance fails, stop the upgraded instance and preserve its data
for diagnosis. Restore the matching pre-upgrade full snapshot and configuration
with the recorded old image while no other writer is active. There is no
automatic down migration; do not run the old image against the upgraded DB.

A database restore cannot undo Graph changes already applied after the backup.
Record those changes and review calendar reconciliation before resuming the
old snapshot; otherwise stale mappings can duplicate events or lose updates.
Never delete calendar content broadly to make a restore look consistent.
The accepted isolated restore test did not start another live calendar writer.
