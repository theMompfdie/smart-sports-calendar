# v0.4.5 Authoritative-Source Stabilization Roadmap

## Purpose

This roadmap turns the released `v0.4.0-alpha.1` workflow into a controlled,
provider-neutral authoritative-source deployment before Phase 5 adds more
competitions.

The target is `v0.4.5-beta.1`; the planned `v0.4.0-beta.1` is superseded and
will not be released. The coordinating GitHub tracker is
[#72](https://github.com/theMompfdie/smart-sports-calendar/issues/72).

## Current and target states

### Current state

- Phase 4 is complete and `v0.4.0-alpha.1` is published.
- Deterministic CI covers the provider-to-SQLite-to-mocked-Graph workflow.
- Multi-instance Compose isolation is implemented and validated.
- Live staging proved Graph targeting and persistent state, while the
  API-Football Free plan did not expose the required current Premier League
  season.
- Provider-neutral source selection and the replacement Premier League
  authority remain outstanding. Issue #73 rejected automated ECAL retrieval
  under the current public terms and identified `football-data.org` as the next
  candidate to qualify.

### Target state

```text
GitHub develop
      |
      | automatic update during normal development
      v
smart-calendar-staging
      |
      | validation and explicit release approval
      v
immutable beta, RC, or release tag
      |
      | manual promotion after backup
      v
smart-calendar-prod
```

Staging and production are independent deployments. They do not share writable
storage, SQLite databases, Outlook calendars, credentials, configuration, or
log streams.

## Work breakdown and dependencies

### 1. Operating-model documentation – #62

Status: completed by #62 and merged PR #65.

Deliverables:

- repository roadmap and stabilization boundary;
- Portainer staging/production model;
- live-validation and sanitized-evidence rules;
- backup, rollback, qualification, and promotion gates; and
- current project instructions in `AGENTS.md`.

This step defines the target state but does not claim that concurrent Compose
deployments already work.

### 2. Multi-instance implementation – #2

Status: completed by #2 and merged PR #66.

Depends on completed #62.

Deliverables:

- conflict-free Compose project, container, image, volume, and network naming;
- independent configuration, credentials, SQLite storage, calendars, and logs;
- health checks that honor the configured database path;
- non-secret instance context for diagnostics;
- deterministic tests for isolation; and
- a successful three-container credential-free Docker validation.

No automated test may call a live provider or Microsoft Graph.

### 3. Source orchestration and Premier League integration – #72

Depends on the completed isolation foundation from #61 and #2.

Deliverables:

- one authoritative source writer per competition and season;
- provider-neutral registration, configuration, scheduling, and import jobs;
- a qualified, permitted Premier League authority and validated adapter;
- stable external identity and complete-snapshot rules for its transport;
- non-destructive coexistence with existing API-Football mappings; and
- deterministic unit, repository, integration, and regression coverage.

The official ECAL subscription is excluded unless explicit written permission
is obtained. `football-data.org` is the next candidate, not an implicitly
approved source.

Automatic failover, simultaneous aggregation, additional released
competitions, live-score enrichment, and website scraping are excluded.

### 4. Staging deployment and live validation – #63

Depends on #2.

The operator creates `smart-calendar-staging` with its own Portainer
configuration, volume, database, Outlook test calendar, and credentials.
Normal staging operation may follow `develop` automatically.

The live gate includes:

1. Graph startup and calendar-target validation with the provider disabled.
2. Persistent SQLite verification across a normal restart.
3. One complete authoritative Premier League import and successful Outlook
   handoff.
4. A second unchanged cycle without duplicates or unnecessary updates.
5. Controlled restart, recovery, backup, and restore observations.
6. Review of provider quota consumption and secret-safe logs.

Only sanitized run identifiers, counters, timestamps, operation categories,
quota numbers, pass/fail results, and follow-up issue numbers may be recorded.

### 5. RC qualification and production promotion – #64

Depends on successful #63 validation.

For final qualification, automatic staging updates are paused and staging is
pinned to the immutable candidate tag. The candidate must pass CI, Docker
validation, live gates, release-note review, and the known-limitations review.

Production promotion is manual:

1. Verify the approved immutable tag and corresponding `main` commit.
2. Stop the production instance and create a verified SQLite backup.
3. Confirm that production has its own stack, volume, database, calendar, and
   secrets.
4. Change only the approved source tag and redeploy explicitly.
5. Verify health, migrations, Graph calendar targeting, first import, and
   synchronization results.
6. Resume service only when the go/no-go checks pass.
7. Use the documented rollback decision if a critical check fails.

Production GitOps updates remain disabled. Production never tracks `develop`.

## Go/no-go gates

### Beta gate

- #72 and #63 acceptance criteria are complete; the #61/#2 isolation
  foundation remains verified.
- Ruff, formatting verification, pytest, Compose validation, Docker health, and
  GitHub Actions pass.
- Three isolated non-live instances have run concurrently.
- Staging Graph/provider validation and the unchanged second cycle pass.
- Backup and recovery evidence is available without sensitive identifiers.
- Known limitations are explicit in the release notes.

### Production-promotion gate

- no unresolved critical or high-severity deployment defect;
- staging is pinned to and validates the exact approved candidate tag;
- production backup is verified before the update;
- production isolation and target calendar are confirmed;
- automatic production updates are disabled; and
- an operator explicitly approves and performs the promotion.

Any failed gate stops promotion. It must not be bypassed by disabling tests,
sharing state, suppressing errors, or changing credentials without recording
the operational decision safely.

## Ownership and secret boundary

Repository work prepares code, tests, configuration examples, and runbooks.
The operator owns Portainer access, Microsoft 365 registration, calendar IDs,
source subscription details, provider subscriptions, real secrets,
backups, and the final promotion decision.

Repository and GitHub evidence must never contain tenant IDs, mailbox
addresses, calendar IDs, client secrets, API keys, tokens, authorization
headers, or secret-bearing URLs.
