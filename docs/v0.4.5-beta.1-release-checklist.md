## Accepted beta limitation

The controlled live provider network-failure exercise was not performed. It is
tracked in #101 and must be described in the release notes. Deterministic retry,
fail-closed, scheduler-isolation, and idempotency coverage reduces risk but is
not a substitute for live evidence. This limitation does not block publishing
the beta pre-release; it blocks manual production promotion.

## Release pull request

Open a ready pull request from `release/64-v0.4.5-beta.1` to `main` titled:

```text
release: v0.4.5-beta.1 – Authoritative Source Beta
```

The pull request must summarize the source authority, isolation model, live
staging evidence, validation record, known limitations, upgrade impact, and
rollback boundary. Use `Refs #64` and `Refs #72`; do not close #64 because its
manual production-promotion work remains open.

## Signed tag and immutable staging qualification

After the release pull request is merged and the resulting `main` commit is
verified:

```bash
git switch main
git pull --ff-only origin main
git tag -s v0.4.5-beta.1 -m "v0.4.5-beta.1 - Authoritative Source Beta"
git push origin v0.4.5-beta.1
```

- [ ] Verify the tag signature and confirm it points to the intended `main`
  commit.
- [ ] Freeze `smart-calendar-staging` to `v0.4.5-beta.1`; do not use
  `develop` during candidate qualification.
- [ ] Verify startup health, migration level, authority selection, Graph target,
  380-fixture unchanged import, and unchanged calendar synchronization.
- [ ] Run and review `python -m app.operations.staging_evidence --database
  /data/sports.db`.
- [ ] Confirm staging remains isolated from every production resource.

If candidate verification fails, do not move or recreate the tag. Fix the
defect through a new reviewed release version.
